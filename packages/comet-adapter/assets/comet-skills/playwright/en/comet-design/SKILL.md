## Prerequisites

- Active change exists (`proposal.md`, `design.md`, `tasks.md`)
- No Design Doc exists under `docs/superpowers/specs/`

## Steps

### 0. Entry State Verification (Entry Check)

```bash
COMET_ENV="${COMET_ENV:-$(find . "$HOME"/.*/skills "$HOME/.config" "$HOME/.gemini" -path '*/comet/scripts/comet-env.sh' -type f -print -quit 2>/dev/null)}"
if [ -z "$COMET_ENV" ]; then
  echo "ERROR: comet-env.sh not found. Ensure the comet skill is installed." >&2
  return 1
fi
. "$COMET_ENV"
if [ -z "$COMET_STATE" ] || [ -z "$COMET_GUARD" ] || [ -z "$COMET_HANDOFF" ]; then
  echo "ERROR: Comet scripts not found. Ensure the comet skill is installed." >&2
  return 1
fi
"$COMET_BASH" "$COMET_STATE" check <name> design
```

Proceed only after verification passes.

**Idempotency:** All design operations may be safely re-executed. If `handoff_context` and `handoff_hash` exist, verify they match current artifacts before regenerating.

### 1a. Generate OpenSpec → Superpowers Handoff Package

**Must be generated by script. Agent-authored replacement summaries are prohibited.**

```bash
"$COMET_BASH" "$COMET_HANDOFF" <change-name> design --write
```

Default mode generates:

```text
openspec/changes/<name>/.comet/handoff/design-context.json
openspec/changes/<name>/.comet/handoff/design-context.md
```

Beta context compression generates:

```text
openspec/changes/<name>/.comet/handoff/spec-context.json
openspec/changes/<name>/.comet/handoff/spec-context.md
```

The script writes `handoff_context` and `handoff_hash` to `.comet.yaml`.

The default package is a compact traceable excerpt, not an agent summary. It retains source paths, line ranges, hashes, deterministic excerpts, `[TRUNCATED]` markers when needed, and full-source references.

The beta package is a structured projection. OpenSpec delta specs remain canonical. If projection data is missing, stale, or unclear, regenerate it or read the source spec directly; never replace it with an agent summary.

For full context:

```bash
"$COMET_BASH" "$COMET_HANDOFF" <change-name> design --write --full
```

Sources include `proposal.md`, `design.md`, `tasks.md`, and `specs/*/spec.md`.

### 1b. Execute Brainstorming (with Context)

**Immediately execute:** Load Superpowers `brainstorming`. Skipping this step is prohibited.

ARGUMENTS must include:

```text
Language: Use the language of the user request that triggered this workflow
```

Use the generated handoff and preserve OpenSpec as the upstream source of truth. Do not weaken brainstorming clarification as “redundant context exploration.”

Cover implementation architecture, data flow, technology choices, risks, testing strategy, boundary conditions, requirement/scope gaps, and Spec Patch candidates.

If goals, scope, non-goals, acceptance scenarios, or constraints remain unclear, continue asking questions. Do not create the Design Doc after only one Q&A turn.

Do not rewrite proposal/spec. Spec Patches may only supplement acceptance scenarios, correct ambiguity, or add boundary conditions. Major structure or scope changes are design findings that require renewed brainstorming confirmation.

Design Doc frontmatter must remain minimal:

```yaml
---
comet_change: <change-name>
role: technical-design
canonical_spec: openspec
---
```

Follow the original brainstorming flow: clarification, two or three approaches, trade-off comparison, and step-by-step confirmation. Do not write the final Design Doc early.

If `brainstorming` is unavailable, stop and ask the user to install or enable Superpowers skills. Do not substitute ordinary conversation.

Incrementally maintain:

```text
openspec/changes/<name>/.comet/handoff/brainstorm-summary.md
```

Update it after each clarification or proposal iteration when confirmed facts, constraints, candidate approaches, trade-offs, risks, testing strategy, or Spec Patch candidates change. Mark unconfirmed content as pending or candidate. It is a recovery checkpoint, not the Design Doc and not a replacement for confirmation.

### 1c. User Confirms Design Proposal (Blocking Point)

Follow `comet/reference/decision-point.md` and wait for explicit confirmation before creating the final Design Doc, writing `design_doc`, running either design gate, or entering `/comet-build`.

Present only the adopted technical approach, key trade-offs and risks, testing strategy, and Spec Patches to write back. Continue brainstorming when adjustments are requested.

### 1d. Brainstorming Checkpoint Finalization

After confirmation, finalize `openspec/changes/<name>/.comet/handoff/brainstorm-summary.md` with:

```md
# Brainstorm Summary

- Change: <change-name>
- Date: <YYYY-MM-DD>

## Confirmed Technical Approach

## Key Trade-offs and Risks

## Testing Strategy

## Spec Patches
```

Use `None` when no Spec Patch exists.

For recovery, reload `brainstorm-summary.md`, `design-context.md` or beta `spec-context.md`, and the matching JSON handoff.

### 1e. Active Context Compaction Gate

After the checkpoint is durable, trigger the host platform's native context compaction once when available. Do not simulate compaction with shell commands.

The resume prompt must include the change name, `Design Step 2`, and the handoff files above. If compaction cannot be triggered programmatically, pause for manual compaction; continue only when the user confirms it is unavailable or asks to continue.

### 1f. Playwright Authoring Plan

If `harness-comet.config.ts` resolves to `mode: "playwright"` and `proposal.md` contains an enabled `Playwright Authoring Decision`:

1. Immediately load `playwright-authoring-plan` in `comet` context.
2. Use the original requirement, `Playwright Impact Analysis`, confirmed target decisions, confirmed technical approach, OpenSpec artifacts, Design handoff, and repository evidence.
3. Do not introduce targets absent from the confirmed authoring decision.
4. Produce a target-by-target plan containing:
   - requirement-to-assertion mapping
   - boundary classification
   - execution route and production sources
   - exact test targets and operations (`verify`, `update`, `create`, `retire`, `ignore`)
   - files to create, update, or retire
   - fixture, test-data, Page Object, and network strategy
   - related assets and evidence paths
   - verification commands and expected evidence
5. Reconcile the plan with the confirmed technical design and Spec Patches. Conflicts must return to brainstorming and user confirmation rather than silently changing scope.

If authoring was skipped or disabled, create an explicit no-op plan stating why no Playwright assets will change.

Do not modify Playwright assets during Design.

### 2. Create Design Doc

Create `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` from the full confirmed brainstorming context using only the minimal frontmatter above.

For Playwright mode include:

```md
## Playwright Authoring Plan
```

The section must preserve target-specific operations and contain the complete confirmed plan or explicit no-op rationale.

Write confirmed Spec Patches back to `specs/*/spec.md`. Do not create a second requirements spec in the Design Doc.

If context was compacted, recover from the finalized checkpoint and generated handoff. If user confirmation is not durable, return to Steps 1b/1c.

### 3. Update Comet State and Run Gates

```bash
"$COMET_BASH" "$COMET_STATE" set <name> design_doc docs/superpowers/specs/YYYY-MM-DD-topic-design.md
```

If a Spec Patch changed `specs/*/spec.md`, regenerate the handoff:

```bash
"$COMET_BASH" "$COMET_HANDOFF" <change-name> design --write
```

For Playwright mode run the Harness-Comet gate before the native guard:

```bash
pnpm exec harness-comet comet hook design --change <change-name>
```

If it fails, fix the Design Doc, Playwright plan, OpenSpec artifacts, or decision consistency and rerun it. Do not edit `.harness-comet/manifest.json` to simulate success.

Then run:

```bash
"$COMET_BASH" "$COMET_GUARD" <change-name> design --apply
```

## Exit Conditions

- Design Doc exists with required minimal frontmatter
- `handoff_context` and `handoff_hash` are present and current
- generated handoff files retain source and sha256 traceability
- beta handoff is structurally valid when enabled
- confirmed Spec Patches are written back
- `design_doc` is written to `.comet.yaml`
- in Playwright mode, the Design Doc contains a complete target-specific plan or explicit no-op
- every enabled target has a plan entry
- no undeclared target is introduced
- the Harness-Comet design gate passes in Playwright mode
- the native guard passes with `--apply` and advances to `phase: build`

`--apply` is mandatory.
