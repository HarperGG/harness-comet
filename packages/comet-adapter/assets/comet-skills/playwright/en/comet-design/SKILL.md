## Prerequisites

- Active change exists (`proposal.md`, `design.md`, `tasks.md`)
- No Design Doc exists under `docs/superpowers/specs/`

## Steps

### 0. Entry State Verification (Entry Check)

Execute entry verification:

```bash
COMET_ENV="${COMET_ENV:-$(find . "$HOME"/.*/skills "$HOME/.config" "$HOME/.gemini" -path '*/comet/scripts/comet-env.sh' -type f -print -quit 2>/dev/null)}"
if [ -z "$COMET_ENV" ]; then
  echo "ERROR: comet-env.sh not found. Ensure the comet skill is installed." >&2
  return 1
fi
. "$COMET_ENV"

if [ -z "$COMET_STATE" ] || [ -z "$COMET_GUARD" ] || [ -z "$COMET_HANDOFF" ]; then
  echo "ERROR: Comet scripts not found. Ensure the comet skill is installed." >&2
  return 1
fi

"$COMET_BASH" "$COMET_STATE" check <name> design
```

Proceed only after verification passes.

**Idempotency:** All design operations may be safely re-executed. If `handoff_context` and `handoff_hash` already exist, confirm they match current artifacts before deciding whether to regenerate.

### 1a. Generate OpenSpec → Superpowers Handoff Package

**The package must be generated by script. Agent-authored replacement summaries are prohibited.**

```bash
"$COMET_BASH" "$COMET_HANDOFF" <change-name> design --write
```

The script reads the `context_compression` snapshot from the change `.comet.yaml` and records the matching handoff package.

Default `context_compression: off` generates:

```text
openspec/changes/<name>/.comet/handoff/design-context.json
openspec/changes/<name>/.comet/handoff/design-context.md
```

Beta mode generates:

```text
openspec/changes/<name>/.comet/handoff/spec-context.json
openspec/changes/<name>/.comet/handoff/spec-context.md
```

It writes `handoff_context` and `handoff_hash` to `.comet.yaml`.

The default package is a compact traceable excerpt, not an agent summary. It must retain source paths, line ranges, hashes, deterministic excerpts, `[TRUNCATED]` markers when needed, and full-source references.

The beta package is a structured projection. OpenSpec delta specs remain canonical. If the projection is missing, stale, or unclear, regenerate it or read the source spec directly; never replace it with an agent summary.

For full context, explicitly run:

```bash
"$COMET_BASH" "$COMET_HANDOFF" <change-name> design --write --full
```

Sources include `proposal.md`, `design.md`, `tasks.md`, and `specs/*/spec.md`.

### 1b. Execute Brainstorming (with Context)

**Immediately execute:** Load the Superpowers `brainstorming` skill. Skipping this step is prohibited.

ARGUMENTS must include:

```text
Language: Use the language of the user request that triggered this workflow
```

Provide the generated handoff paths and preserve OpenSpec as the upstream source of truth. Do not weaken the original brainstorming clarification flow by claiming context exploration is redundant.

The brainstorming work must cover:

- implementation architecture and data flow
- key technology choices and risks
- testing strategy
- boundary conditions
- requirement or scope gaps
- Spec Patch candidates

If goals, scope, non-goals, acceptance scenarios, or constraints remain unclear, continue asking questions. Do not create the Design Doc after only one Q&A turn.

Do not rewrite proposal/spec. Spec Patches may only supplement acceptance scenarios, correct ambiguity, or add boundary conditions. Major structural or scope changes must be reported as design findings and returned to brainstorming for confirmation.

Design Doc frontmatter must remain minimal:

```yaml
---
comet_change: <change-name>
role: technical-design
canonical_spec: openspec
---
```

Follow the original brainstorming flow: clarifying questions, two or three approaches, trade-off comparison, and step-by-step confirmation. Do not write the final Design Doc early.

If the brainstorming skill is unavailable, stop and ask the user to install or enable Superpowers skills. Do not substitute ordinary conversation.

During brainstorming, incrementally maintain:

```text
openspec/changes/<name>/.comet/handoff/brainstorm-summary.md
```

Update it after each clarification or proposal iteration whenever confirmed facts, constraints, candidate approaches, trade-offs, risks, testing strategy, or Spec Patch candidates change. Mark unconfirmed content as pending or candidate. This file is a recovery checkpoint, not the Design Doc and not a replacement for user confirmation.

### 1c. User Confirms Design Proposal (Blocking Point)

Follow `comet/reference/decision-point.md` and wait for explicit user confirmation before creating the final Design Doc, writing `design_doc`, running either design gate, or entering `/comet-build`.

Present only the essential summary:

- adopted technical approach
- key trade-offs and risks
- testing strategy
- Spec Patches to write back, if any

If adjustments are requested, continue brainstorming until confirmed.

### 1d. Brainstorming Checkpoint Finalization

After confirmation, finalize:

```text
openspec/changes/<name>/.comet/handoff/brainstorm-summary.md
```

It must contain:

```md
# Brainstorm Summary

- Change: <change-name>
- Date: <YYYY-MM-DD>

## Confirmed Technical Approach

## Key Trade-offs and Risks

## Testing Strategy

## Spec Patches
```

Use `None` when no Spec Patch exists.

For recovery after compaction, reload:

- `brainstorm-summary.md`
- `design-context.md` or beta `spec-context.md`
- `design-context.json` or beta `spec-context.json`

### 1e. Active Context Compaction Gate

After the checkpoint is durable, trigger the host platform's native context compaction once when available. Do not simulate compaction with shell commands.

The resume prompt must include the change name, current step (`Design Step 2`), and the handoff files above.

If the platform cannot compact programmatically, pause and ask the user to perform the platform's manual compaction action. Continue only after the user confirms compaction is unavailable or asks to continue.

### 1f. Playwright Authoring Plan

If `harness-comet.config.ts` resolves to `mode: "playwright"` and `proposal.md` contains an enabled `Playwright Authoring Decision`:

1. Immediately load `playwright-authoring-plan` in `comet` context.
2. Use the original requirement, `Playwright Impact Analysis`, confirmed target decisions, confirmed technical approach, OpenSpec artifacts, Design handoff, and repository evidence.
3. Do not introduce targets absent from the confirmed authoring decision.
4. Produce a target-by-target plan containing:
   - requirement-to-assertion mapping
   - boundary classification
   - execution route and production sources
   - exact test targets and operations (`verify`, `update`, `create`, `retire`, `ignore`)
   - files to create, update, or retire
   - fixture, test-data, Page Object, and network strategy
   - related assets and evidence paths
   - verification commands and expected evidence
5. Reconcile the plan with the confirmed technical design and Spec Patches. If they conflict, return to brainstorming and user confirmation rather than silently changing scope.

If Playwright authoring was explicitly skipped or disabled, create an explicit no-op plan stating why no Playwright assets will be changed.

Do not modify Playwright assets during Design.

### 2. Create Design Doc

Create `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` from the full confirmed brainstorming context.

Use only the minimal frontmatter shown above.

For Playwright mode, include:

```md
## Playwright Authoring Plan
```

The section must preserve target-specific operations and contain the complete confirmed plan or explicit no-op rationale.

Write confirmed Spec Patches back to the corresponding `specs/*/spec.md` files. Do not create a second requirements spec in the Design Doc.

If context was compacted, recover from the finalized checkpoint and generated handoff package. If user confirmation is not durable, return to Steps 1b/1c.

### 3. Update Comet State and Run Gates

Record the Design Doc path:

```bash
"$COMET_BASH" "$COMET_STATE" set <name> design_doc docs/superpowers/specs/YYYY-MM-DD-topic-design.md
```

If a Spec Patch changed `specs/*/spec.md`, regenerate the handoff:

```bash
"$COMET_BASH" "$COMET_HANDOFF" <change-name> design --write
```

For Playwright mode, run the Harness-Comet design gate before the native guard:

```bash
pnpm exec harness-comet comet hook design --change <change-name>
```

If it fails, fix the Design Doc, Playwright plan, OpenSpec artifacts, or decision consistency and rerun it. Do not edit `.harness-comet/manifest.json` to simulate success.

Then run the native Comet guard:

```bash
"$COMET_BASH" "$COMET_GUARD" <change-name> design --apply
```

## Exit Conditions

- Design Doc exists with required minimal frontmatter
- `handoff_context` and `handoff_hash` are present and current
- generated handoff files retain source and sha256 traceability
- beta handoff is structurally valid when enabled
- confirmed Spec Patches are written back
- `design_doc` is written to `.comet.yaml`
- in Playwright mode, the Design Doc contains a complete target-specific plan or explicit no-op
- every enabled target has a plan entry
- no undeclared target is introduced
- the Harness-Comet design gate passes in Playwright mode
- the native Comet design guard passes with `--apply` and advances to `phase: build`

`--apply` is mandatory.

Follow `comet/reference/context-recovery.md` with phase `design`.

Follow `comet/reference/auto-transition.md`:

```bash
"$COMET_BASH" "$COMET_STATE" next <change-name>
```

- `NEXT: manual` → do not invoke it; prompt the user to run `/<SKILL>`
- `NEXT: done` → workflow is complete
